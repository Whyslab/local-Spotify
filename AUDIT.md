## Как проводился аудит

1. Прочитан весь код сервиса (`adder/`), фронтенд (`web/`), скрипты (`scripts/`), деплой (`deploy/`), CI и оба README.
2. Установка с нуля строго по README в чистом venv (Python 3.12), запуск `python -m adder.server`,
   реальные запросы `/health`, `/api/add`, `/api/tasks`.

4. Точечные проверки поведения: классификация реальных сообщений yt-dlp, санитизация имён,
   перехват сетевых соединений во время тестов.

## HIGH

### H1. CI красный: `ruff format --check` падает
- **Где:** `adder/app.py:825-829` (`logger.info(...)` в `process`), `adder/app.py:1227-1235` (`rows.append({...})` в `library_index`).
- **Суть:** последний функциональный коммит не прогнан через `ruff format`; шаг Lint в CI падает, тесты в CI не запускаются вовсе.
- **Фикс:** `ruff format adder scripts tests`.

### H2. Сервис стартует с публично известным токеном-заглушкой
- **Где:** `adder/config.py:57-62`.
- **Суть:** проверяется только пустота `API_TOKEN`. Если скопировать `.env.example` и не поправить его (README Quick start не запускает `install.sh`, где такая проверка есть), API в LAN открыт с токеном `CHANGE_ME_TO_A_LONG_RANDOM_SECRET`, который лежит в публичном репо.
- **Фикс:** отказываться стартовать с заглушкой — та же проверка, что уже есть в `deploy/install.sh`.

### H3. `.env.example` задаёт путь-заглушку `LIBRARY_PATH=/home/your-user/...`
- **Где:** `.env.example:5`, `adder/app.py:1019` (`LIBRARY.mkdir(parents=True)` в `lifespan`).
- **Суть:** без правки у обычного пользователя старт падает с `PermissionError: '/home/your-user'`, под root сервис молча создаёт чужой каталог и пишет туда музыку, которую Navidrome не видит.
- **Фикс:** закомментировать `LIBRARY_PATH` в примере — тогда работает задокументированный дефолт `~/Music/Normalized Library`, одинаковый для Python и `install.sh`.

### H4. Ошибки yt-dlp: причина теряется, классификация неверная
- **Где:** `adder/app.py:531`, `adder/app.py:551` (`p.stderr.strip()[-300:]`), `adder/app.py:740-777` (`classify_error`).
- **Суть (проверено на реальных сообщениях yt-dlp):**
  - В задачу пишутся последние 300 символов stderr. Строка `ERROR:` длинная, поэтому пользователь видит хвост вида `...for tips on effectively exporting YouTube cookies`, а сама причина («Sign in to confirm you're not a bot») обрезана.
  - `ffprobe and ffmpeg not found` → `youtube_not_found` (из-за подстроки «not found»): пользователю говорят, что видео нет.
  - `Private video` для видео с `503` в ID → `network_error` и три бессмысленных повтора: подстроки `502/503/504` ищутся где угодно, включая ID и URL.
  - Rate limit обрабатывается непоследовательно: `Unable to download API page: HTTP Error 429` → `download_error` (повтор), `HTTP Error 429: Too Many Requests` → `unknown_error` (без повтора), `This content isn't available, try again later` (так YouTube сообщает об ограничении сессии) → `youtube_not_found` (без повтора).
  - Бот-проверка и возрастное ограничение → `unknown_error`, без подсказки про `COOKIES_FROM_BROWSER`.
- **Фикс:** брать из stderr последнюю строку `ERROR:` (если её нет — хвост, как раньше). В `classify_error` добавить типы `dependency_error` (ffmpeg — постоянная), `rate_limited` (429 / too many requests / try again later — повторяемая) и `youtube_auth_required` (бот-проверка, возраст, members-only — постоянная). HTTP 5xx сопоставлять только по `http error 50x`. К ошибке бот-проверки добавлять подсказку про `COOKIES_FROM_BROWSER`.
- **Не меняется:** экспоненциальный backoff (2 с, 4 с) — для rate limit он коротковат, см. M3.

### H5. Отсутствие ffmpeg/ffprobe и Deno не обнаруживается
- **Где:** `adder/app.py:1014-1045` (`lifespan`), `adder/app.py:1298-1337` (`/health`).
- **Суть:** сервис стартует «healthy», а каждая задача потом падает на постобработке. Про Deno вообще ничего нигде нет.
- **Фикс:** при старте проверить `shutil.which` для `ffmpeg`/`ffprobe` (без них — `ERROR` в логе и `/health` = `unhealthy` с полем `ffmpeg: missing`) и для `deno` (без него — `WARNING` в логе и поле `js_runtime` в `/health`, но статус healthy: часть видео может скачаться и без него).

### H6. Небезопасные имена файлов из метаданных YouTube
- **Где:** `adder/app.py:180-184` (`sanitize_filename`), использование в `adder/app.py:839-841`.
- **Суть:** имя исполнителя — это название канала, то есть недоверенные данные. Проверено:
  - `sanitize_filename("..")` → `".."` → `LIBRARY / ".." / "Singles"` — запись **за пределы библиотеки**;
  - заголовок из одних запрещённых символов (`"?"`) → `""` → файл `.m4a` — скрытый, Navidrome его не покажет;
  - имя, начинающееся с точки, — тоже скрытое;
  - длинное имя (эмодзи/кириллица) может превысить 255 байт → `OSError: File name too long` → задача падает как `unknown_error`.
- **Фикс:** в `sanitize_filename` убирать ведущие/хвостовые точки и пробелы, обрезать до 200 байт UTF-8 по границе символа, пустой результат превращать в `Unknown`.

### H7. Воркер-поток умирает от неожиданного исключения
- **Где:** `adder/app.py:987-1010` (`worker`), обработчики ошибок в `process` (`adder/app.py:904-984`).
- **Суть:** если внутри обработчика ошибки падает сам `task_update` (например, `database is locked`) или что-то выше по стеку бросает исключение, оно выходит из `worker()` и **поток завершается**. После `MAX_WORKERS` таких случаев очередь встаёт навсегда, `/health` остаётся «healthy», а URL остаётся в `PROCESSING_URLS`: повторная отправка той же ссылки молча игнорируется до перезапуска.
- **Фикс:** в `worker()` оборачивать `process()` в `try/except Exception`: логировать с трейсбэком, по возможности помечать задачу `error`, всегда освобождать URL и продолжать цикл.

### H8. Удаление треков не работает под systemd-юнитом
- **Где:** `adder/app.py:1177` (`TRASH_DIR = PROJECT.parent / "trash"`), `deploy/music-adder.service.template:25-31`.
- **Суть:** юнит запускается с `ProtectSystem=strict` и `ReadWritePaths` только на `adder/` и библиотеку. Корзина лежит в корне репозитория, куда писать нельзя → `DELETE /api/library` в продакшене отдаёт 500 (read-only file system). Тестов на удаление нет, поэтому это незаметно.
- **Фикс:** перенести корзину в `adder/trash/` (уже в `ReadWritePaths`, уже в `.gitignore` через шаблон `trash/`). Юнит не меняется.

### H9. Итог задачи не пишется в лог
- **Где:** `adder/app.py:780-984` (`process`).
- **Суть:** логируются только повторы. Успешное добавление (куда лёг файл) и **финальная ошибка** в `journalctl` не попадают вообще — только в SQLite. Диагностировать «почему трек не появился» по логам невозможно. Строка с метаданными Deezer идёт без `task_id`.
- **Фикс:** логировать начало задачи, путь итогового файла, дубликат и финальную ошибку (`logger.error` с `error_type`); передавать `task_id` во все сообщения `process`.

### H10. Тесты ходят в сеть и не покрывают ключевую логику
- **Где:** `tests/test_duplicate_integration.py` вызывает `process()` без мока `enrich.describe`/`fetch_cover_url` — проверено перехватом `socket.connect`: 4 реальных соединения за прогон.
- **Суть:** тесты медленные/флейки без сети и шлют запросы к Deezer из CI. Нет тестов на построение команды yt-dlp и разбор её ошибок, на `enrich.lookup` (парсинг ответа Deezer), на реальную запись тегов в M4A и раскладку файла в библиотеке, на удаление.
- **Фикс:** `tests/conftest.py` с autouse-фикстурой, которая запрещает внешние сокеты (падение вместо тихого запроса); новые тесты с моками `run_yt_dlp`, `enrich._get`, `requests.get` и маленьким настоящим M4A-файлом в `tests/fixtures/`.

### H11. README не позволяет установить проект без догадок
- **Где:** `README.md`, `README.ru.md`.
- **Суть:** не указаны Deno, команды установки ffmpeg, что именно менять в `.env`, как поставить и подключить Navidrome, что нужен `sqlite3` для бэкапа, как обновлять yt-dlp, что делать при бот-проверке YouTube; захардкожено «96 тестов».
- **Фикс:** переписать установку пошагово с проверкой каждого шага, добавить раздел «Troubleshooting».

### H12. `install.sh` перезаписывает конфиг Navidrome и игнорирует `LIBRARY_PATH`
- **Где:** `deploy/install.sh:48-55`.
- **Суть:** если Navidrome установлен, скрипт **безусловно** перезаписывает `/etc/navidrome/navidrome.toml` — существующая настройка пользователя теряется. При этом `MusicFolder` подставляется как `$HOME/Music/Normalized Library`, даже если в `.env` задан другой `LIBRARY_PATH` — Navidrome смотрит не туда, куда сервис кладёт треки.
- **Фикс:** подставлять тот же `LIBRARY_PATH_VALUE`, что и в юнит; если конфиг уже есть — не трогать его, а напечатать, какую строку `MusicFolder` проверить.

## MEDIUM (не исправлялось)

### M1. Дедупликация почти никогда не срабатывает на реальных дублях
- **Где:** `adder/app.py:617-657`, `adder/app.py:868-895`, `adder/app.py:660-665`.
- **Суть:** хеш считается по файлу **после** записи тегов и обложки, а разные видео с одной песней (клип, lyric video, «Topic»-канал) и так дают разное аудио. Повторная отправка той же ссылки отсекается по URL в БД; хеш спасает только при потере БД. В итоге одна песня из двух ссылок ложится как `Song.m4a` и `Song (1).m4a`. ID видео в теги не пишется, поэтому связь «файл ↔ видео» теряется вместе с БД.
- **Предложение:** писать ID видео во freeform-тег (`----:com.apple.iTunes:YOUTUBE_ID`) и проверять его перед скачиванием; перед финальным переносом сравнивать нормализованные `artist + title` (+ длительность ±2 с) и помечать задачу `duplicate`, а не молча создавать `(1)`. Меняет поведение — нужно ваше решение.

### M2. `/api/add` частично добавляет пакет перед ошибкой 400
- **Где:** `adder/app.py:1107-1169`.
- **Суть:** ссылки валидируются по одной внутри цикла вставки. Если 5-я ссылка невалидна, первые 4 уже в очереди, а клиент получает 400 без их ID.
- **Предложение:** сначала провалидировать и канонизировать все ссылки, потом вставлять.

### M3. Backoff слишком короткий для rate limit, нет паузы между загрузками
- **Где:** `adder/app.py:937-959`, `adder/config.py` (`RETRY_BACKOFF_BASE`).
- **Суть:** повтор через 2 и 4 с после 429 только продлевает бан. Два воркера качают без пауз.
- **Предложение:** для `rate_limited` отдельная задержка (минуты), глобальная пауза после 429 для всех воркеров, опционально `--sleep-requests` у yt-dlp.

### M4. Лишнее перекодирование с потерями
- **Где:** `adder/app.py:535-547`.
- **Суть:** `-x --audio-format m4a` перекодирует Opus (лучший поток YouTube) в AAC: lossy → lossy.
- **Предложение:** `-f "bestaudio[ext=m4a]/bestaudio"` — брать нативный AAC, если он есть, и перекодировать только иначе.

### M5. Нет ограничения на длительность и прямые эфиры
- **Где:** `adder/app.py:796-802`.
- **Суть:** 10-часовой микс или стрим занимает воркер до таймаута 600 с × 3 попытки.
- **Предложение:** проверять `meta["is_live"]` и `meta["duration"]` до скачивания, лимит в конфиге.

### M6. Исполнитель из названия канала
- **Где:** `adder/app.py:251-274` (`split_artist_title`).
- **Суть:** для видео без `Artist - Title` исполнителем становится канал: `Artist - Topic`, `ArtistVEVO`, название лейбла. Это же уходит в поиск Deezer → промах → «fallback».
- **Предложение:** срезать суффиксы ` - Topic` и `VEVO`; для лейблов — нет надёжного решения без ручной правки.

### M7. Обложка iTunes берётся без сверки, содержимое не проверяется
- **Где:** `adder/app.py:561-600`, дубль в `adder/fix_covers.py:23-42`.
- **Суть:** `limit=1` и первый результат без проверки исполнителя/названия → у малоизвестных треков чужие обложки. Ответ `200` с HTML вместо картинки вшивается как JPEG.
- **Предложение:** сравнивать `artistName/trackName` через `enrich.normalize`, проверять сигнатуру JPEG/PNG.

### M8. Проверка свободного места смотрит не на тот диск
- **Где:** `adder/app.py:669-682`.
- **Суть:** проверяется `TMP_DIR` (в репозитории), а библиотека часто на другом диске. Любая ошибка проверки = «места хватает».
- **Предложение:** проверять и `TMP_DIR`, и `LIBRARY`.

### M9. SQLite без WAL и `busy_timeout`, соединение на каждый запрос
- **Где:** `adder/app.py:113-129`.
- **Суть:** параллельные воркеры и API при нагрузке ловят `database is locked` (таймаут по умолчанию 5 с). H7 устраняет последствия, но не причину.
- **Предложение:** `PRAGMA journal_mode=WAL`, `timeout=30` в `sqlite3.connect`.

### M10. Кэш yt-dlp и Deno под `ProtectSystem=strict` доступен только на чтение
- **Где:** `deploy/music-adder.service.template`.
- **Суть:** `~/.cache/yt-dlp` и `~/.cache/deno` read-only. yt-dlp выдаёт предупреждение и каждый раз заново скачивает данные плеера; поведение Deno без кэша не проверено (нет systemd в песочнице).
- **Предложение:** `--cache-dir adder/cache` и `DENO_DIR=adder/cache/deno` в окружении юнита. Проверить руками на реальной машине.

### M11. `backup.sh` требует `sqlite3` CLI
- **Где:** `deploy/backup.sh:22`.
- **Суть:** без пакета `sqlite3` скрипт падает на `set -e`. Теперь указано в README.
- **Предложение:** использовать `python -c "sqlite3...backup()"` из venv — без новой системной зависимости.

### M12. Дублированный код в `scripts/`
- **Где:** `scripts/migrate_playlist.py:38-100` vs `adder/app.py` (`sanitize_filename`, `itunes_cover`, `fetch_cover`, `unique_path`), `adder/fix_covers.py`.
- **Суть:** копии уже разошлись (`sanitize_filename` в скрипте возвращает `Unknown` для пустой строки, в сервисе нет). Фиксы H6 в скрипты не попали.
- **Предложение:** вынести общие функции в модуль `adder/`, импортировать из скриптов.

### M13. `install.sh`: порт 8787 захардкожен, кавычки в `LIBRARY_PATH` ломают юнит

### M14. Тестовые зависимости в рантайм-requirements
