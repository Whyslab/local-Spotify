# Скрипты

## analyze_audio.py — измерить фонотеку

У 1109 треков нет ни жанра, ни BPM. Сортировать нечем — кроме самого звука.
Скрипт слушает каждый трек и записывает темп, энергию, яркость и тональность,
чтобы очередь можно было собирать не случайно.

### Запуск

```bash
# так, как задумано: с потолком памяти и пониженным приоритетом
systemd-run --user --scope -p MemoryMax=1500M \
  nice -n 10 .venv/bin/python scripts/analyze_audio.py --jobs 3
```

Зависимости стоят отдельно от сервиса — librosa тянет numba и scikit-learn,
а сервису они не нужны:

```bash
.venv/bin/pip install -r scripts/requirements-analysis.txt
```

### Сколько это займёт

Измерено на этой машине (i5-6300U, 2 ядра): **около 3 секунд на трек**,
то есть примерно **час на всю фонотеку** в один процесс и **порядка 55 минут**
на двух. Пиковая память одного процесса — **376 МБ**, поэтому три помещаются
в лимит 1500 МБ, а без лимита earlyoom скорее убьёт браузер, чем анализ.

Оценка в плане работ была 15–30 минут. Она оказалась вдвое оптимистичной.

### Прогон можно прерывать

Каждый трек записывается сразу и опознаётся по пути и хешу содержимого.
Прерванный прогон продолжается с места остановки, а неизменившийся трек не
измеряется повторно. Убить процесс безопасно.

С `--jobs` больше единицы выход не мгновенный: уже начатые треки дописываются,
и это занимает секунды. Остальные снимаются сразу.

```bash
scripts/analyze_audio.py --limit 50      # остановиться после 50 треков
scripts/analyze_audio.py --only ФАЙЛ     # один файл
scripts/analyze_audio.py --force         # пересчитать всё заново
```

### Ночью, само

Таймер ставит `deploy/install.sh` — вместе со службой и остальными таймерами,
со всеми подстановками в шаблоне (`%REPO%`, `%LIBRARY%`, `%JOBS%`). Руками
шаблон лучше не собирать: без `%LIBRARY%` служба не может записать теги
ReplayGain, и `systemd-run` отказывается от строки целиком. Число процессов —
`ANALYSIS_JOBS` при запуске установщика (по умолчанию 3):

```bash
ANALYSIS_JOBS=1 ./deploy/install.sh
```

Ночной проход обычно только пересчитывает хеши и занимает меньше минуты; на
машине, где свободно меньше двух гигабайт, одного процесса хватает.

Новый трек измеряется сразу при добавлении — тем же способом, в своей области
с тем же лимитом, — так что таймер нужен только для догона того, что появилось
до его включения.

### Что именно измеряется

| | |
| --- | --- |
| **темп** | ударов в минуту; половинный и двойной темп считаются одним и тем же |
| **энергия** | среднеквадратичная громкость — насколько трек «давит» |
| **яркость** | спектральный центроид: два трека одного темпа и громкости всё равно разные, если один басовый, а другой в тарелках |
| **тональность** | нота и лад, по корреляции хромаграммы с профилями Крумхансль–Шмуклера |

Анализируется **середина трека**, 90 секунд. Этого с запасом хватает на темп и
тональность, память ограничена независимо от длины трека, а вступление и
концовка — наименее показательные части песни для обоих.

Декодирует **ffmpeg**, а не встроенный загрузчик librosa: тот читает через
libsndfile, который не умеет AAC, а почти вся фонотека в `.m4a`.

## render_transition.py — связка перехода «как диджей»

Его зовёт служба, руками он не нужен. Плеер на ноутбуке, когда включён переход
«как диджей», просит связку для пары «этот трек → следующий»; служба запускает
скрипт так же, как разбор (свой scope с потолком памяти, `nice`), и кладёт
результат в `adder/transitions/`.

Связка — короткий FLAC: чистый конец трека A (4 с), сам переход, чистое начало
трека B (8 с). По краям плеер стыкует связку с треками, поэтому края — ровно
те же отсчёты, что в файлах. Как выбирается способ перехода (вступление без
барабана, удар в удар, короткий переход) — в начале самого скрипта.

Нужны пакеты разбора (`scripts/requirements-analysis.txt`: librosa, scipy,
soundfile) и `ffmpeg` с фильтром `rubberband` (растяжение без смены высоты).
Проверить руками одну пару:

```bash
echo '{"a": "/путь/A.m4a", "b": "/путь/B.m4a", "out": "/tmp/x.flac"}' \
  | .venv/bin/python scripts/render_transition.py
```

## export_shelves.py — полки главной в подборки

Полки главной («В машину», «Разогнаться», «На работу», «Поярче», «Может
понравиться») считаются на лету, и на телефоне их нет вовсе: Amperfy видит
только то, что Navidrome нашёл в фонотеке, а там подборка — это файл. Скрипт
пересобирает те же пять полок в файлы `★ ....m3u` в корне фонотеки.

Альбомы с главной не выгружаются: альбом Navidrome и так знает по тегам, и
подборка из него была бы второй копией того же.

Заодно скрипт заготавливает миниатюры обложек (96 и 300 точек) для треков,
у которых их ещё нет, — `adder/thumb-cache/`. Служба делает их и сама при
добавлении трека, ночной проход ловит добавленное мимо неё.

### Руками

```bash
.venv/bin/python scripts/export_shelves.py
```

Печатает по строке на полку и код возврата: `0` — записана хотя бы одна,
`1` — ни одной. Полка меньше восьми треков пропускается, и вчерашний файл
остаётся на месте: вчерашняя подборка лучше пустой.

### Ночью, само

Позже разбора звука, а не раньше: полки строятся из `audio_features`, поэтому
запуск до анализа собрал бы их по вчерашним измерениям. Таймер стоит на 04:30,
анализ — на 03:30.

Ставит его тоже `deploy/install.sh`.

Служба ходит только в две папки — корень фонотеки и `adder/playlist-history`, —
поэтому `%LIBRARY%` в шаблоне обязателен: без подстановки `ProtectHome=read-only`
не даст записать ни одного файла.

### Правки в подборках со звездой затираются

Файл `★ ...` пересобирается целиком при каждом запуске. Переставленный трек,
удалённый трек, дописанная строка — всё это исчезнет следующей ночью. Прежнее
содержимое уходит в `adder/playlist-history/★ .../`, так что затёртую правку
оттуда можно достать — но история хранит двадцать последних версий, а запуск
каждую ночь свой, то есть примерно три недели. Постоянной подборке лучше дать
своё имя, без звезды: приставка `★` и означает «этот файл принадлежит скрипту».

## upgrade_audio.py — фонотека в оригинальный Opus с YouTube

Большая часть фонотеки лежала как Opus, пережатый в AAC: полоса целая, но
пики выше полной шкалы сплющены (в громком треке — сотни тысяч отсчётов), и
это второе сжатие поверх первого. Скрипт находит каждый трек на YouTube
заново, качает Opus и кладёт его в тот же `.m4a` без перекодирования.

Трек заменяется, только если это доказуемо та же запись: длина ±3 с, в
названии видео нет другой версии (clean, sped up, remix…), звук совпадает
с нынешним файлом — ≥ 0,97 в целом и ≥ 0,8 в каждой громкой секунде (так
ловится «чистая» версия с запиканными словами). Не трогаются загруженные
вручную файлы, ALAC и треки, для которых у YouTube нет Opus.

Ссылку скрипт берёт из тега `SOURCE_URL`, из задачи, которой трек был скачан,
или из `adder/known-links.csv` — там лежат ссылки из импорта Spotify, которых
нет ни в тегах, ни в задачах (файл не в git). Не подошла ни одна — ищет по названию.

Сохраняется всё: теги, обложка, дата добавления; громкость (ReplayGain)
меряется заново, анализ темпа переезжает на новый файл. Старый файл до
замены копируется в `~/.local/share/local-Spotify/opus-upgrade/backup/`.

### Запуск

```bash
# фоном, переживёт закрытие терминала
systemd-run --user --unit=opus-upgrade -p WorkingDirectory=$PWD \
  -p MemoryMax=1500M -p Nice=10 $PWD/.venv/bin/python scripts/upgrade_audio.py
journalctl --user -u opus-upgrade -f | grep -v download   # смотреть ход

.venv/bin/python scripts/upgrade_audio.py --dry-run --limit 5   # проверить, не меняя
.venv/bin/python scripts/upgrade_audio.py --retry               # ещё раз «не найденные»
```

Около 12 секунд на трек, то есть 4–5 часов на тысячу. Прогон можно
прервать и запустить снова: сделанное записано в `state.json` рядом с
бэкапом. Сам останавливается, если YouTube просит войти или режет запросы.
В конце просит Navidrome перечитать все файлы — иначе он не заметит
замену: дата у файлов прежняя.

### Вернуть один трек

```bash
cp -p ~/.local/share/local-Spotify/opus-upgrade/backup/"Артист/Singles/Трек.m4a" \
  ~/"Music/Normalized Library/Артист/Singles/Трек.m4a"
```

## quality_audit.py — качество звука фонотеки (только чтение)

Для каждого трека: кодек, битрейт, частота, длина; сколько энергии осталось
выше 16 и выше 19 кГц относительно полосы 1–16 кГц (спектр по трём отрезкам
по 10 с); пики по всему треку — насколько высоко, сколько отсчётов выше
полной шкалы и сколько в «плоских верхушках».

Что помечается:

- `cut16` — выше 16 кГц на 60 дБ и больше тише полосы (у обычной музыки здесь
  −15…−45 дБ): трек сжимали со срезом на 16 кГц — AAC с YouTube или залитая
  туда пережатая копия;
- `clipped` — тысяча и больше отсчётов в плоских верхушках (три равных подряд
  у предела): так выглядит настоящая обрезка пиков. Отсчёты выше 1,0 после
  декодера Opus — не она: так звучит почти любой громкий мастер с YouTube, а
  плеер громкость только убавляет; их число в отчёте, но не помечается;
- `low_bitrate`, `low_rate` — битрейт ниже обычного для кодека, частота ниже 44,1 кГц.

Совет у помеченного: AAC — `upgrade_audio.py` (у YouTube, скорее всего, есть
Opus лучше, и тот скрипт докажет, что это та же запись); остальное со срезом
— «other source»: плох сам залитый файл. Скрипт ничего не меняет.

```bash
# фоном: ~4 с на трек, около полутора часов на всю фонотеку
systemd-run --user --unit=quality-audit -p WorkingDirectory=$PWD \
  -p MemoryMax=1500M -p Nice=10 $PWD/.venv/bin/python scripts/quality_audit.py --json $HOME/quality.json
journalctl --user -u quality-audit -f          # итог и список помеченных — в конце

.venv/bin/python scripts/quality_audit.py --limit 20   # быстро взглянуть
```

## stress.py — нагрузка на живую службу и уборка после неё

Сценарии S1–S7 из плана (раздел 7.2): фонотека целиком, поиск по ней, обложки
тёплые и холодные, звук с Range под нагрузкой обложек, смешанные запросы,
пробные добавления и перезапуск с задачей в очереди. На каждый — p50/p95/p99,
ошибки, размеры ответов, пик памяти и ЦП службы (`systemctl --user show`) и её
дочерние процессы, в том числе одновременные `ffmpeg` (по `/proc/<pid>/task/*/children`,
не `pgrep -f`). Ключ берётся из `adder/.env` и не попадает ни на экран, ни в
отчёт: отчёт с ним скрипт отказывается записать.

### Порядок

```bash
./deploy/backup.sh                                   # страховка — до всего
.venv/bin/python scripts/stress.py snapshot          # .omc/stress/snapshot.json
.venv/bin/python scripts/stress.py run --scenarios S1,S2,S3,S4,S5
.venv/bin/python scripts/stress.py run --scenarios S6,S7 \
  --probe-links links.txt --allow-restart
.venv/bin/python scripts/stress.py residue           # код возврата 1 — что-то осталось
```

Отчёт — `.omc/stress/report-<время>.json` (или `--report ПУТЬ`), короткая таблица —
на экран. Другая служба — `--base-url`. С 02:45 до 05:15 скрипт не запускается:
это окно ночных таймеров (снимок базы, анализ), и пробы не должны в него попасть.

Запускать — из той же папки, откуда работает служба
(`systemctl --user show music-adder -p WorkingDirectory`): `run`, `snapshot`,
`cleanup` и `residue` отказываются, если рядом нет `adder/adder.db`, а для
службы по умолчанию — и если папка не та, что у юнита. Из рабочей копии
(`local-Spotify-work`) они не пойдут.

### Что делает каждый сценарий

| | |
| --- | --- |
| **S1** | `/api/library` целиком и по 200 строк, по 200 запросов при 1, 5 и 20 параллельно |
| **S2** | 200 подстрок в 1–6 букв из названий фонотеки, 5 параллельно (время — на стороне клиента) |
| **S3** | 500 обложек, `size=96` и `300`, 6 и 24 параллельно. Тёплые — на живой службе (первый проход прогревает кэш и тоже в отчёте); холодные — на изолированном экземпляре |
| **S4** | 10 параллельных `/api/stream` с Range, пока идёт S3 (без S3 — 20 кругов): время до первого байта |
| **S5** | `/api/home`, `/api/playlists`, `/health`, `/api/tasks` вперемешку, 10 параллельно, 2 минуты (`--s5-seconds`) |
| **S6** | пробы на фоне звука из S4: битая ссылка должна кончиться `youtube_not_found`, повтор — не встать в очередь; подборка `zz-stress-probe` создаётся и заполняется через API |
| **S7** | только с `--allow-restart`: ждёт тишины (нет активных задач, нет `GET /api/stream` в журнале за 60 с, нет соединений в `ss`), ставит пробу, перезапускает службу, меряет время до `/health` и ждёт, что задача дойдёт до `done` |

**Изолированный экземпляр** (холодные обложки) — приложение в процессе самого
скрипта, `lifespan="off"`: не стартуют ни воркеры, ни «Артист целиком», ни обход
текстов, ни ListenBrainz. Все пути `runtime` и копии `lyrics.CACHE_DIR`,
`covers.COVERS_DIR`, `playlists.HISTORY_DIR` смотрят во временную папку; фонотека —
настоящая, только на чтение; спрашивается у него только `/api/cover`. Клиент и
сервер делят один процесс, поэтому эти цифры (S3 cold) — для сравнения
«до/после», а не абсолютные; в отчёте у каждого такого прогона это записано в
`note`, и таблица печатает ту же оговорку.

### Пробы

Ссылки выбирает человек — короткие треки со свободной лицензией, которых нет в
фонотеке; в скрипте ни одной ссылки нет. Файл для `--probe-links`:

```text
# по ссылке на строку, не больше пяти (429 от YouTube останавливает все скачивания)
https://www.youtube.com/watch?v=...
https://youtu.be/...
broken: https://www.youtube.com/watch?v=несуществующий
```

С S7 последняя ссылка уходит на перезапуск. Скрипт откажется пробовать, если нет
снимка, снимку больше 2 часов или фонотека с него изменилась (обновить —
`stress.py snapshot --force`), прежние пробы не убраны, в журнале за 2 часа есть
ограничение YouTube, ссылка уже есть в фонотеке или в `tasks`, а для S6 — если
подборка `zz-stress-probe` уже есть (в снимке или в службе). Своей эта подборка
считается только после успешного `POST /api/playlists`: чужую с тем же именем
уборка не тронет. Манифест `.omc/stress/probes.json`
пишется **до** первого `POST /api/add`; задачи и пути проб записываются в него по
`task_id` и `result_path` из `/api/tasks`, не по названию. `/api/plays` и
`/api/player-event` скрипт не вызывает.

### Уборка

Идёт сама в конце `run` (кроме `--keep-probes`) и вручную —
`stress.py cleanup`. Трогает только то, что названо в манифесте: подборку
`zz-stress-probe`, треки проб (`DELETE /api/library`), ровно эти файлы в `trash/`,
строки проб в `tasks`, `plays`, `audio_features`, их миниатюры и тексты. Трек,
который был в фонотеке до снимка (проба оказалась дубликатом), остаётся на месте.
Без снимка треки не удаляются вовсе. Прерванную уборку можно запустить снова.

Манифесту на слово не верится. Трек удаляется, только если строка задачи пробы
в `tasks` ведёт на этот путь со ссылкой на то же видео и тег `source` файла в
`/api/library` — тоже это видео; иначе он остаётся, а уборка пишет ошибку. Пока
трек на месте, строка его задачи тоже остаётся: ею он и проверяется. Подборка
удаляется только с постоянным именем `zz-stress-probe` (другое имя в манифесте —
ошибка), миниатюры — только с именами вида sha1 (40 шестнадцатеричных знаков).

Navidrome удалённые файлы не забывает, а показывает как «отсутствующие». Уборка
вычищает и их — только записи с путями проб (`DELETE /api/missing?id=…`, как
страница Missing Files в админке Navidrome), подождав до минуты, пока сканер
заметит удаление; старые «отсутствующие» не трогаются. Заодно удаляется история
версий пробной подборки (`adder/playlist-history/zz-stress-probe`). Чистым
манифест отмечается только после этого шага. Пробу, которую Navidrome за минуту
не показал «отсутствующей», скрипт ищет у него в песнях (`GET /api/song?path=…`,
пропавшие тоже там): нет ни песни, ни записи — файл удалили раньше, чем до него
дошёл сканер, и это не ошибка (`navidrome_never_scanned` в манифесте). Если же
Navidrome этот путь знает, спросить его не вышло или его логина нет в
`adder/.env`, `cleanup` пишет `incomplete` и его надо запустить ещё раз (без логина — сначала вписать
`NAVIDROME_USER`/`NAVIDROME_PASSWORD`). До этого
`residue` остаётся красным: число «отсутствующих» должно совпасть со снимком, а
если его не удалось прочитать (нет `NAVIDROME_USER`/`NAVIDROME_PASSWORD` в
`adder/.env`, нет доступа к `/api/missing`), `residue` тоже красный и просит
проверить руками. Ещё `residue` требует `navidrome_pending == 0` в `/health` и
чтобы последний проход синхронизации (`GET /api/sync`, только чтение) не нашёл
расхождений у `zz-stress-probe`; результат прохода обновляется по таймеру, так
что сразу после уборки он может быть ещё старым. Поиск проб через Subsonic
`search3` скрипт не делает (нужна отдельная подпись запросов) — его, если надо,
руками. Наутро `residue` проверяет и свежий ночной снимок
`adder/snapshots/adder_*.db`.

## measure_ui.py и measure_window.py — цели скорости

Меряют то, что обещано про скорость открытия, обложек, прокрутки и поиска.
Только читают: ничего не добавляют, не играют и не пишут прослушиваний.

| Метрика | Что от чего | Цель |
| --- | --- | --- |
| `ready_cold` | начало перехода (у окна — начало загрузки страницы) → метка `app-ready` в новом пустом профиле | ≤ 1.5 с |
| `ready_warm` | то же повторно, с прогретым кэшем | ≤ 0.5 с |
| `start_cold`, `start_warm` | только у окна: запуск процесса (Python, GTK, WebKit) → начало загрузки страницы | без цели |
| `covers` | последнее событие прокрутки → ни одной недогруженной обложки на экране | ≤ 0.3 с |
| `long_tasks` | задачи длиннее 50 мс (у окна — разрывы кадров) при прокрутке всей фонотеки | 0 |
| `search`, `search_library` | ввод последней буквы → нарисованный результат | ≤ 0.15 с |

```bash
.venv/bin/python scripts/measure_ui.py                 # браузер: профили laptop и phone, по 10 прогонов
.venv/bin/python scripts/measure_ui.py --budget        # выход 1, если хоть одна цель не выполнена
.venv/bin/python scripts/measure_ui.py --smoke         # страница дошла до «готово» без ошибок
.venv/bin/python scripts/measure_window.py             # окно на ноутбуке, 10 + 10 запусков и прокрутка
```

`phone` — Chromium под iPhone 13 с процессором медленнее в 4 раза и 60 мс
задержки сети. Задержку даёт прокси перед службой: через него идут и запросы
service worker'а, которых задержка CDP не касается (для `https`-адреса прокси
не встать — там задержка CDP, только на запросы страницы). `measure_window.py` запускает `desktop/local-spotify.py` в режиме
замера (`LOCAL_SPOTIFY_PERF=1`) на своём виртуальном экране Xvfb (пакет
`xorg-server-xvfb`; без него скрипт отказывается и окон на рабочий стол не
выводит) и с временными `XDG_DATA_HOME`/`XDG_CACHE_HOME`: настоящий профиль окна
и скачанное в нём не трогаются. На Xvfb отрисовка программная, так что цифры
окна скорее хуже настоящих. Из копии проекта без `adder/.env` ключ указывается
явно: `--env /путь/к/adder/.env`.

## compare_screens.py — две версии плеера, экран за экраном

Для правок, которые не должны менять вид (например, удаление мёртвого CSS).
Две ревизии выкладываются во временные папки, каждая поднимает свою службу на
одинаковой заглушечной фонотеке, Chromium открывает все экраны обхода из
`tests/test_ui.py` на ширине ноутбука и телефона и сравнивает снимки
попиксельно. Вторая страница той же базы — контроль: где она не совпала с
базой, экран «нестабилен», и сказать о нём ничего нельзя.

```bash
.venv/bin/python scripts/compare_screens.py                       # HEAD~ против HEAD
.venv/bin/python scripts/compare_screens.py --base main --head work --keep shots/
```

Выход 0 — разницы нет нигде; нестабильный экран — тоже выход 1. Сдвиг цвета
на 1–2 единицы за разницу не считается; экран снимается до трёх раз с
перерисовкой, и разница засчитывается, только если держится. Сравнивается
только видимая часть окна (ниже первого экрана — нет), список экранов берётся
из `tests/test_ui.py` рабочей копии. Нужны ffmpeg и Chromium Playwright. Живую
службу и фонотеку не трогает.
